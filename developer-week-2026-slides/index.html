So the problem is clear — hope doesn't scale. But before we jump to the solution, let's frame it properly. Every event-driven system needs to answer three questions. What's the shape of the data? That's JSON Schema. Who produces it, who consumes it, through what channels? That's AsyncAPI. And how do we know it actually works? That's Microcks. The Unifier: JSON Schema

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "AgentConfiguration",
  "type": "object",
  "required": [
    "agentId", "name", "modelProvider",
    "modelId", "temperature"
  ],
  "properties": {
    "agentId": {
      "type": "string",
      "pattern": "^[a-z0-9-]+$"
    },
    "name": {
      "type": "string",
      "minLength": 1, "maxLength": 100
    },
    "modelProvider": {
      "type": "string",
      "enum": ["OPENAI", "ANTHROPIC", "GOOGLE", "MISTRAL"]
    },
    "modelId": {
      "type": "string"
    },
    "temperature": {
      "type": "number",
      "minimum": 0, "maximum": 2
    }
  }
}
This is the fix. One JSON Schema file. Five required fields — agentId, name, modelProvider, modelId, and temperature. That's our contract. Notice: this isn't Java. It isn't Python. It's a language-neutral description of the data shape. MongoDB can enforce it as a collection validator. AsyncAPI can reference it for event payloads. Microcks can generate mocks from it. And both services validate against the same file. One schema. One source of truth.

Here's where it gets interesting. That one JSON Schema file does four jobs. First, MongoDB uses it as a collection validator — bad documents get rejected at write time. Second, AsyncAPI references it to define the event payload — documentation that's always current because it points at the actual schema. Third, Microcks imports the AsyncAPI spec and generates mock events — so the Edge team can develop without the Hub even running. And fourth, Microcks runs contract tests — validating that real events from the Hub match the schema. One file. Four uses. Zero duplication.

AsyncAPI 3.0: Documentation as Code

asyncapi: 3.0.0
info:
  title: Agent Configuration Events

channels:
  agentConfigChanges:
    address: hub_db.agentConfigs
    messages:
      insertEvent:
        $ref: '#/components/messages/AgentConfigInsertEvent'

operations:
  onAgentConfigChange:
    action: receive
    channel:
      $ref: '#/channels/agentConfigChanges'

components:
  messages:
    AgentConfigInsertEvent:
      payload:
        $ref: '#/components/schemas/AgentConfiguration'

  schemas:
    AgentConfiguration:
      $ref: 'agent-config.schema.json'

$ref — no copy, no drift. Same schema MongoDB enforces.

AsyncAPI 3.0 describes how configuration changes propagate as events. Notice the structure — channels are separated from operations, which is new in version 3. But the key line is at the bottom: the schema reference. It's a dollar-ref pointing directly at our JSON Schema file. No copy. No duplication. The AsyncAPI spec and MongoDB are enforcing the exact same contract. When Microcks imports this spec, it understands the full picture — what channels exist, what operations consumers can perform, and what the payload looks like.

Microcks is the piece that ties it all together. It's a CNCF sandbox project — production-grade, cloud-native. Here's the workflow. You import your AsyncAPI spec. Microcks reads the schema and generates mock events. Now the Edge team can develop their consumer without the Hub service even running — they code against Microcks mocks. Meanwhile, when the Hub is ready, Microcks runs contract tests — validating that real events from the Hub match the spec. If they match, you ship with confidence. If they don't, you find out in CI, not at 3 AM. Two teams, developing in parallel, kept honest by the contract.

Adding a required field breaks existing consumers.

Here's the "aha" moment. A developer adds a new required field to the Hub's schema — let's say "version." They deploy. The Hub starts emitting events with the new field. But old documents don't have it. Microcks runs the contract test and fails — the old events don't match the new required field. The CI pipeline goes red. The breaking change is caught before it reaches production. No 3 AM page. No rollback. No "sorry, we didn't know the consumer depended on that." The contract caught it. And honestly, that's the whole point. The contract isn't documentation you write and forget. It's a safety net that catches you when you drift.

Three takeaways. First: schema as source of truth. One definition, multiple uses. MongoDB enforces it, AsyncAPI references it, Microcks generates mocks and tests from it. No duplication, no drift. Second: contract independence. Java and Python interoperate without knowing about each other. If we agree on the data shape, implementation language becomes an implementation detail. Third: validation at every layer. The database rejects bad writes. The producer validates events. The consumer validates payloads. CI catches drift. Defense in depth. The contract isn't documentation. It's executable specification. It is the system.
